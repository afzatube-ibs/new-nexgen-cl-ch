### Added
- `apps/backend` — **Commerce Core milestone**: Media, Catalog, and Inventory, completed together by explicit Product Owner priority direction (2026-08-03) ahead of their `planning/IMPLEMENTATION_MASTER_PLAN.md` sequence position. Search was explicitly evaluated and excluded from this milestone: Catalog already publishes `ProductCreated`/`ProductUpdated`/`ProductArchived` as the foundation a future Search module (item 29) will consume, and nothing in Catalog's own completeness required a search engine to exist yet.
  - **Media** (`MODULE:MEDIA`, Platform domain) — the platform's single reusable asset store, so Products/Categories/Brands (and, later, CMS/Themes) never each invent their own upload handling. `MediaAsset` aggregate: real file upload via Laravel's filesystem, content-derived (never client-supplied) MIME/size validation rejecting anything outside an explicit image/PDF allowlist (SVG deliberately excluded — a known stored-XSS vector), a randomly-generated storage path (never the caller's filename, closing path-traversal/overwrite risk), `DATA:VERSIONING` optimistic locking on alt-text edits, soft delete plus restore. Publishes `MediaUploaded`/`MediaDeleted`. Permissions `media.assets.view`, `media.assets.manage`, `media.audit_log.view`. API: `GET/POST /api/v1/media`, `GET/PATCH/DELETE /api/v1/media/{media}`, `POST /api/v1/media/{id}/restore`, `GET /api/v1/media-library/audit-logs`.
  - **Catalog** (`MODULE:CATALOG`, Commerce domain) — the platform's largest aggregate family and the foundation Inventory, and eventually Orders/Checkout/Search/Promotions/Storefront, build on: Products (simple/configurable/digital), Categories (hierarchical), Brands, Attributes/Attribute Groups (typed product facts), Options/Option Values (variant dimensions), Variants, Collections, Tags, product images and logos (referenced from Media by identifier — Catalog never duplicates asset storage), product relationships (related/cross-sell/up-sell), SEO fields, free-form metadata, slug generation, a publishing workflow with a real completeness gate (`PublishProductAction` refuses to activate a product with no category, or a configurable product with no variants), `DATA:LIFECYCLE` draft/active/archived status plus soft delete and restore across every aggregate (Product, Category, Brand, Collection, Tag, Option, Attribute, Attribute Group), `DATA:VERSIONING` optimistic locking, and its own audit trail. Publishes `ProductCreated`, `ProductUpdated`, `ProductArchived`, `VariantAdded`. 15 permissions across `catalog.products`, `.categories`, `.brands`, `.attributes`, `.options`, `.collections`, `.tags`, `.audit_log`. Full REST API under `/api/v1/products`, `/categories`, `/brands`, `/attribute-groups`, `/attributes`, `/options` (+ nested option values), `/collections`, `/tags`, plus nested product sub-resources (variants, images, attribute-values, categories/collections/tags/options assignment, relationships) and `/api/v1/catalog/audit-logs`.
  - **Inventory** (`MODULE:INVENTORY`, Commerce domain, single-warehouse Phase 1 scope with multi-warehouse already exercised at schema level) — Warehouses; `StockItem` deliberately keyed by SKU (never a Catalog foreign key, keeping the "Inventory depends on Catalog" relationship event-driven, not structural); concurrency-safe stock reservation (`lockForUpdate` row locking, not optimistic locking, so concurrent holds serialize instead of rejecting each other) implementing the master plan's "concurrent checkout reservations never oversell" acceptance criterion; stock adjustments with full movement history; reservation release/commit; warehouse-to-warehouse stock transfers (initiate places a hold, complete moves stock with deadlock-safe lock ordering, cancel releases the hold); a cross-warehouse availability lookup for the future Checkout module. Publishes `StockAdjusted`, `StockReserved`, `StockReleased`. 7 permissions across `inventory.warehouses`, `.stock`, `.reservations`, `.transfers`, `.audit_log`. API under `/api/v1/warehouses`, `/stock-items` (+ adjust/reservations), `/reservations/{id}/release|commit`, `/stock-transfers` (+ complete/cancel), `/inventory/availability`, `/inventory/audit-logs`.
  - Verified before commit: `composer test` (deptrac boundaries — 0 violations across all six modules — plus the full Pest suite, 251 tests passing against real MySQL/Redis), `composer analyse` (PHPStan/Larastan level 8, 0 errors), Pint (442 files, clean), and a live end-to-end HTTP smoke test exercising all three modules together (upload an image to Media, attach it as a Brand logo and Product image, build a configurable Product with an Option/Variant, publish it, adjust/reserve/commit Inventory stock, confirm availability reflects the commit).

- `apps/backend` — **Organizations & Stores** module implementing `MODULE:STORE_CONFIGURATION` (Phase 1, Implementation Order item 3). Owns the store-level business profile (identity, currency, locale, timezone, contact, registered address) as a `Store` aggregate root with `DATA:VERSIONING` optimistic locking, `DATA:LIFECYCLE` Active/Archived/Deleted states, and its own `DATA:AUDIT_DATA`-compliant audit trail, separate from Identity & Access's. Depends only on Identity & Access (authentication/authorization), per the Implementation Master Plan. Publishes `StoreConfigurationChanged` on create/update. New permissions `store_configuration.stores.view`, `store_configuration.stores.manage`, `store_configuration.audit_log.view`, synced via `store-configuration:sync-permissions` and `db:seed`. API: `GET/POST /api/v1/stores`, `GET/PATCH/DELETE /api/v1/stores/{store}`, `POST /api/v1/stores/{store}/archive`, `GET /api/v1/store-configuration/audit-logs`. Verified before commit: `composer test` (deptrac boundaries + full Pest suite, all passing against real MySQL/Redis), `composer analyse` (PHPStan/Larastan level 8, 0 errors), Pint (passing), and a live end-to-end HTTP smoke test (boot, login, create/read/update/optimistic-lock-conflict/archive/audit-log/delete).
