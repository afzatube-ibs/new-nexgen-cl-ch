# Changelog

All notable changes to the neXgen Core project are recorded here. This tracks repository and documentation milestones — see individual documents' own Change Log sections for document-level revision history.

## [Unreleased]

### Added
- `apps/backend` — **Notifications & Email** (`MODULE:NOTIFICATIONS`, Operations domain), per `planning/reviews/PHASE1_BACKEND_COMPLETION_REPORT.md` §6 item 4. `docs/04_MODULE_ARCHITECTURE.md` had never formally defined this module's boundary despite `planning/IMPLEMENTATION_MASTER_PLAN.md` naming it (#33) — only a passing mention existed, under Localization & Currency's own entry ("the translation surface Catalog, CMS, and Notifications content read from"). Formally added in v1.4, under Operations rather than Platform or Growth: `ARCH:DOMAIN_MAP`'s own §10 ("Out of Platform: no Platform module may depend on any module outside Platform, directly or via events") structurally rules out Platform, since this module must react broadly to Commerce and Operations events; Growth is ruled out since both `ARCH:DOMAIN_MAP` and `04_MODULE_ARCHITECTURE.md` §7 state Growth capability is "designed for, not built in, Phase 1"; Operations' own domain description — "reacts to events from Commerce... without owning Commerce's data" — is an exact, already-exercised structural match (Fulfillment already does this for `OrderPlaced`).
  - **Three aggregates**: `NotificationTemplate` (one row per code/channel/locale, `{{merge_field}}` placeholders resolved by `Support\TemplateRenderer` — deliberately no template-engine dependency), `Notification` (the aggregate root — one shape covering every channel, per `DATA:AGGREGATE_BOUNDARIES`; a Notification Status Lifecycle `pending → queued → sending → sent`, with `failed` re-entering `queued` for retry and `cancelled` reachable from `pending`/`queued`), and `NotificationDeliveryAttempt` (an append-only ledger, mirrors Payments' `PaymentAttempt`). `recipient`/`related_type`/`related_id` are plain snapshot columns, never a foreign key, per `DATA:CROSS_MODULE_ACCESS` — and, for transactional email specifically, the semantically correct choice: the address on file when the triggering event happened, not a possibly-since-changed live profile.
  - **Channel-agnostic provider architecture** (`Channels\Contracts\NotificationProviderContract` + `ProviderRegistry`/`ProviderFactory`/`ProviderResolver`, mirroring Payments' Gateway trio and Shipping's Courier trio exactly): real, functional `email` providers only — SMTP (Symfony Mailer's own transport, self-contained configuration, no dependency on Laravel's global `config/mail.php`), Mailgun (real Messages API), Amazon SES (via SES's own documented SMTP interface — a genuine integration, not the REST API, to avoid adding the AWS SDK for one call — honestly described as such), and Brevo (real transactional email API). `sms`/`whatsapp` are contract-ready (the channel enum, template support, and the provider interface itself all already accommodate them) but **no live OneCodeSoft, SSL Wireless, BulkSMSBD, or Meta WhatsApp Cloud API adapter is wired** — Phase 1 scope per the master plan's own explicit "Phase 1 (Notifications + Email) / Phase 2 (SMS, WhatsApp)" split and this project's own prior Phase 1 Completion Review ruling ("SMS/WhatsApp explicitly deferred to Phase 2"), confirmed with the Product Owner before implementation began.
  - **Real background queue** (`Jobs\SendNotificationJob implements ShouldQueue`, dispatched onto ADR-0004's Redis backbone) — this platform's first genuine use of Laravel's queue system; every prior module's cross-domain reaction runs synchronously in-process via the domain event bus, deliberately different here since an unreachable email provider must never block the request or event that triggered the notification. Retry Policy is domain-level and auditable, not the queue driver's own opaque mechanism: `Actions\SendNotificationAction` computes backoff from `config('notifications.retry.backoff_seconds')` and leaves the Notification `queued` with `next_retry_at` set; the job reads that back and dispatches a fresh delayed instance of itself. `$tries = 1` on the job itself — a provider failure is not the job's own failure to report to the queue's dead-letter handling, since the Action has already recorded and decided what to do about it.
  - **Eight cross-domain integration listeners** in `app/Listeners/Send*On*.php` subscribe to `OrderPlaced`, `PaymentCaptured`, `PaymentRefunded`, `ShipmentDispatched`, `FulfillmentCompleted`, `ReturnRequested`, `RefundIssued`, and `CustomerRegistered` — resolving the recipient from the triggering module's own already-owned data (chiefly Orders' immutable `customer_email`/`customer_name` snapshot; `CustomerRegistered` already carries the address directly) and calling this module's own `Actions\QueueNotificationAction`, never reaching into another module's data directly. 8 real, seeded default English templates ship with the platform (`Database\Seeders\NotificationTemplateSeeder`) so a fresh installation sends real, usable notifications out of the box.
  - **Two self-review findings, fixed before commit — both genuinely severe, not cosmetic**:
    1. None of the eight listeners originally caught their own exceptions. Since `OrderPlaced`/`PaymentCaptured`/`PaymentRefunded`/etc. are published synchronously, in-process, from *inside* the triggering module's own transaction, an uncaught `NotificationValidationException` (a missing/misconfigured template — a routine, expected condition, not a bug) propagated straight back through the event bus and failed the transaction that published the event. This surfaced as 24 unrelated test failures across Orders, Payments, Checkout, Customers, and Returns — a platform-wide regression a missing module boundary should never have been able to cause. Fixed by wrapping every listener's `QueueNotificationAction` call in a try/catch that reports (logs) and swallows the failure, never rethrows — a notification failure must never be able to break the workflow that triggered it, per this module's own "MUST NOT contain business logic from Orders, Payments, Shipping, Fulfillment, Returns, Customers... never the owner of business workflows" rule.
    2. A related reliability gap in `Actions\SendNotificationAction`: a provider's own HTTP call throwing a raw connection-level exception (rather than returning a `NotificationSendResult` with `status: 'failed'`, as every shipped provider's own internal try/catch is written to do) would leave a Notification permanently stuck in `sending`, unable to ever retry. Fixed with a backstop try/catch around the provider call itself, converting any escaped exception into the same recorded-failure-and-retry path as an ordinary provider-reported failure.
  - 5 permissions across `notifications.templates.view/manage` and `notifications.notifications.view/manage`, plus `.audit_log.view` — separated since authoring content and operating an individual delivery are different responsibilities.
  - API: `GET/POST /api/v1/notification-templates` (+ `{id}`, `PATCH`), `GET/POST /api/v1/notifications` (+ `{id}`, `/retry`, `/cancel`), `GET /api/v1/notification-audit-logs`.
  - Verified before commit: `composer test` (Deptrac boundaries — 0 violations — plus the full Pest suite against real MySQL/Redis, 1078 tests, including dedicated architecture-test rules for the new module and its eight cross-domain listeners), `composer analyse` (PHPStan/Larastan level 8, 0 errors), Pint (clean), `migrate:fresh --seed`, `platform:health`/`/up`/`/api/health` all healthy, and a live end-to-end smoke test using a real Redis-backed queue worker: an ad-hoc notification queued via the API, processed by a genuine `artisan queue:work` process, and honestly marked retryable-failed with a real `NotificationDeliveryAttempt` logged (no email provider is configured in this dev environment) — plus a real `CustomerRegistered` → welcome-notification chain verified end-to-end through the live HTTP API, and optimistic-locking/retry-validation/cancel/audit-log all confirmed live.
- `apps/backend` — **Returns, Exchanges & Refunds** (`MODULE:RETURNS`, Operations domain), per `planning/reviews/PHASE1_BACKEND_COMPLETION_REPORT.md` §6 item 3. Owns return/exchange/refund requests and their status, reacting to Fulfillment/Order-related state rather than depending on Commerce directly. Three independent aggregate roots — `ReturnRequest` (items, RMA number, Return Status Lifecycle `requested → approved → pickup_scheduled → received → inspecting → resolution_approved → completed`, with `rejected`/`cancelled` terminal paths reachable at multiple points, timeline, notes), `RefundRequest`, and `ExchangeRequest` — kept separate per `DATA:AGGREGATE_BOUNDARIES` ("the smallest set of data that genuinely must be consistent at every moment"): RefundRequest changes on an independently-triggered async lifecycle (Payments' own confirmation), warranting its own consistency boundary and `lock_version` distinct from ReturnRequest's operator-driven transitions. Bangladesh-first reasons: damaged, wrong item, courier damage, delivery refusal, changed mind, other; full and partial resolution via refund, exchange, or rejection-after-inspection.
  - **Payments extended additively**: `amount_refunded`/`refunded_at` columns, `STATUS_PARTIALLY_REFUNDED`/`STATUS_REFUNDED` added to `Payment`'s status graph, and `Actions\RefundPaymentAction` — the first caller of `Gateways\Contracts\RefundableGateway`, an extension point that module's own `BkashGateway` implementation had left deliberately unexercised in advance for exactly this. Refund amount validated against the remaining refundable balance via `bcmath` precision arithmetic; publishes `PaymentRefunded`.
  - **Cross-domain refund coordination**, preserving "cross-domain communication only through the event bus, never a direct call": `ResolveReturnRequestAction` publishes `ReturnResolved` (a new event marking the seam between "a resolution was decided" and "the money has actually moved") → `app/Listeners/ProcessRefundOnReturnResolved.php` calls Payments' `RefundPaymentAction` → Payments publishes `PaymentRefunded` → `app/Listeners/CompleteRefundOnPaymentRefunded.php` completes the `RefundRequest` and publishes the master-plan-named `RefundIssued`/`ReturnCompleted`. A refund never occurs without an associated Payments transaction reference, structurally. Courier pickup validates against Shipping's own `Couriers\ProviderRegistry` (same-domain call, permitted within Operations per `MODULE:INTERACTION_RULES`) but records the actual collection via an operator-supplied reference — no courier publishes a verified reverse-pickup API, so this deliberately does not fabricate one, mirroring Fulfillment's own manual-dispatch fallback. `RetryRefundRequestAction` recovers a failed refund by re-publishing `ReturnResolved`.
  - **Self-review finding, fixed before commit**: while building the two new cross-domain listeners above, discovered that Laravel's automatic `app/Listeners` event discovery (on by default since `Application::configure()`) was silently double-registering every listener in that directory alongside this platform's own explicit `DomainEventBus::subscribe()` calls in `AppServiceProvider` — including Fulfillment's pre-existing `CreateShipmentOnOrderPlaced` from 2026-08-07, masked until now only because that handler is naturally idempotent. `ProcessRefundOnReturnResolved` is not idempotent by design (a second refund attempt against an already-completed `RefundRequest` is a genuine error), so the duplicate registration surfaced immediately as a hard test failure. Fixed at the root — `bootstrap/app.php` now calls `->withEvents(discover: false)` — rather than papering over it by making every listener defensively idempotent; `app/Listeners/*` is wired exclusively through this platform's own explicit event-bus contract now.
  - Exchange request/lifecycle (`pending → preparing → shipped → completed`, plus `cancelled`) built now, at Phase 1 scope; exchange-triggered inventory reservation and automatic Fulfillment shipment creation remain the master plan's own named Phase 2 extension point — an operator dispatches the replacement through Fulfillment's existing manual-creation API and records the tracking number here.
  - 7 permissions across `returns.requests.view/manage/approve/inspect/resolve/cancel` and `.audit_log.view` — `.inspect` and `.resolve` separated from `.manage` since `.resolve` gates the action that triggers real money movement or committed inventory.
  - API: `GET/POST /api/v1/return-requests` (+ `{id}`), `POST /api/v1/return-requests/{id}/{approve,reject,cancel,pickup,receive,inspect,resolve}`, `POST /api/v1/return-requests/{id}/notes`, `GET /api/v1/refund-requests` (+ `{id}`, `/retry`), `GET /api/v1/exchange-requests` (+ `{id}`, `/prepare`, `/ship`, `/complete`, `/cancel`), `GET /api/v1/returns/audit-logs`.
  - Verified before commit: `composer test` (Deptrac boundaries — 0 violations — plus the full Pest suite against real MySQL/Redis, 978 tests, including dedicated architecture-test rules for the new module and its cross-domain listeners), `composer analyse` (PHPStan/Larastan level 8, 0 errors), Pint (clean), `migrate:fresh --seed`, `platform:health`/`/up`/`/api/health` all healthy, and a live end-to-end HTTP smoke test covering return-request creation/RMA generation, the full status lifecycle including manual pickup and a 409 optimistic-locking conflict, notes, the audit trail, and a complete exchange-type return through `resolve → prepare → ship → complete` with the parent `ReturnRequest` correctly completing alongside its `ExchangeRequest` — the refund cross-domain chain itself verified via the automated suite's real, application-wired event-bus tests rather than hand-built live Order/Payment fixtures.
- `apps/backend` — **Fulfillment** (`MODULE:FULFILLMENT`, Operations domain), per `planning/reviews/PHASE1_BACKEND_COMPLETION_REPORT.md` §6 item 2. Owns the record of what has been picked, packed, and shipped against an order. `Shipment` aggregate root (order/customer identifiers and shipping-method reference snapshotted by identifier only, never a foreign key — mirrors Payments' own `payment_attempts.order_id` precedent) with owned child aggregates `ShipmentItem` (SKU by plain identifier, mirroring Inventory's `stock_items.sku`), `ShipmentTimelineEvent`, and `ShipmentNote` (both mirroring Orders' own timeline/notes pattern exactly). Full Shipment Status Lifecycle (`pending → picking → picked → packing → packed → dispatched → in_transit → delivered`, plus `failed`/`cancelled` terminal states) with explicit transition guards, weight/destination completeness checks before packing/dispatch, `DATA:VERSIONING` optimistic locking, and a complete audit trail alongside the business-readable timeline. Reacts to Orders' `OrderPlaced` event (never `PaymentCaptured` — Cash On Delivery only captures payment after delivery, so waiting for it would make COD orders unfulfillable) via `app/Listeners/CreateShipmentOnOrderPlaced.php`, a dedicated integration listener living outside every domain's own namespace specifically so neither Orders nor Fulfillment's own code ever references the other — this is the platform's first real, production cross-domain event subscription (`planning/reviews/ARCHITECTURE_REVIEW.md` A-4's anticipated first real subscriber), registered from `App\Providers\AppServiceProvider::boot()`. Courier hand-off happens exclusively through Shipping's own `Couriers\ShippingProviderContract`, extended additively with `bookShipment()`/`supportsBooking()` exactly as that contract's original docblock anticipated — Fulfillment contains no courier-specific business logic at all, and every courier shipped with Shipping (Steadfast, Pathao, RedX, Paperfly, eCourier as production-ready architecture against each one's real documented Create Order API; Manual and Sundarban honestly refusing booking) gained real booking capability with no change to Fulfillment. A manual dispatch path (operator-supplied tracking number) covers self-managed fulfillment and any courier without automated booking. Publishes `FulfillmentStarted`, `ShipmentDispatched`, `FulfillmentCompleted` — named explicitly in the master plan's Fulfillment entry. 7 permissions across `fulfillment.shipments.view/manage/pick/pack/dispatch/cancel` and `.audit_log.view` — pick/pack/dispatch/cancel deliberately separated from `.manage` to match real warehouse role separation. API: `GET/POST /api/v1/shipments` (+ `{id}`), `POST/DELETE /api/v1/shipments/{id}/items(/{item})`, `POST /api/v1/shipments/{id}/notes`, `PATCH /api/v1/shipments/{id}/destination`, `POST /api/v1/shipments/{id}/{pick/start,pick/complete,pack/start,pack/complete,dispatch,in-transit,deliver,fail,cancel}`, `GET /api/v1/fulfillment/audit-logs`. Verified before commit: `composer test` (Deptrac boundaries — 0 violations, including the new cross-domain listener's deliberately "uncovered" placement — plus the full Pest suite against real MySQL/Redis, 896 tests), `composer analyse` (PHPStan/Larastan level 8, 0 errors), Pint (clean), architecture tests (Pest arch, including a dedicated rule keeping the cross-domain listener a thin translator), and a live end-to-end HTTP smoke test covering the entire pick/pack/dispatch/in-transit/deliver workflow, courier-unavailable-fails-safely and manual-dispatch-succeeds paths, optimistic-locking conflict, and the full audit/timeline trail.
- `apps/backend` — **Shipping & Logistics** (`MODULE:SHIPPING`, Operations domain — the platform's first Operations-domain module), per `planning/reviews/PHASE1_BACKEND_COMPLETION_REPORT.md` §6 item 1. Scoped strictly to the accepted `docs/04_MODULE_ARCHITECTURE.md` boundary — "owns shipping method configuration and rate information" — deliberately excluding the Shipment aggregate, status lifecycle, tracking, and label execution, which that same document reserves for the future Fulfillment module (`MODULE:FULFILLMENT`); building those here would have duplicated a boundary the accepted architecture already draws elsewhere. `ShippingZone` (geographic jurisdiction, mirrors Pricing's `TaxZone`), `ShippingMethod` (named service level, e.g. Standard/Express, optionally naming a courier `provider_code`), `ShippingRate` (weight-banded price per zone+method — "Shipping Rates" and "Shipping Rules" implemented as one concept, mirroring Pricing's `TaxRate`/"Tax Rules" precedent). Provider-agnostic Courier Registry (`Couriers\ShippingProviderContract` + `ProviderRegistry`/`ProviderFactory`/`ProviderResolver`, mirroring Payments' Gateway trio exactly): Manual (always available, no external integration), Steadfast, Pathao, RedX, Paperfly, and eCourier as production-ready architecture against each courier's real documented API shape, gated by `isAvailable()`; Sundarban registered for identity/selection only (publishes no public merchant API — confirmed against its own documentation, honestly reported rather than faked). None of the six couriers publish a live per-shipment rate-quote API (confirmed against each one's own documentation), so `Actions\CalculateShippingRateAction` — this module's "Rate query" Public Contract — resolves against this platform's own configured `ShippingRate` card and returns null (never a fabricated zero) when no rate is configured, exactly the seam a future live-quoting courier would plug into with no change to this action. Per the accepted `MODULE:INTERACTION_RULES` ("across domains, communication happens only through the domain event bus"), this module has zero code-level dependency on any Commerce module (Checkout included) — Checkout's `Support\ShippingOptionCatalog` temporary stand-in is therefore intentionally left unmodified by this delivery; consuming this module's own `/api/v1/shipping/*` API is a client/API-consumer composition concern, not a backend cross-domain call. Publishes `ShippingRateCalculated`, named explicitly in the master plan's Shipping & Logistics entry. `DATA:VERSIONING` optimistic locking, `DATA:LIFECYCLE` active/archived plus soft delete, `restrictOnDelete` guards surfaced as typed `DependentRecordsExistException`, full audit trail. 8 permissions across `shipping.zones`, `.methods`, `.rates`, `.providers`, `.audit_log`. API: `GET/POST /api/v1/shipping-zones` (+ `{id}`, archive, delete), `GET/POST /api/v1/shipping-methods` (+ same), `GET/POST /api/v1/shipping-rates` (+ same), `POST /api/v1/shipping/quote`, `GET /api/v1/shipping/providers`, `GET /api/v1/shipping/audit-logs`. Verified before commit: `composer test` (Deptrac boundaries — 0 violations — plus the full Pest suite against real MySQL/Redis), `composer analyse` (PHPStan/Larastan level 8, 0 errors), Pint (clean), architecture tests (Pest arch), and a live end-to-end HTTP smoke test.
