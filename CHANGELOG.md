### Fixed
- **Live-backend auth verification (post-Phase-2.1) — a real post-login crash found and fixed.** Phase 2.1's own Playwright suite passed entirely against network-mocked responses; this pass stood up a real `apps/backend` instance for the first time (PHP 8.4 + Composer installed locally; SQLite + file/sync drivers used only because no MySQL/Redis server or working Docker engine was available in this sandboxed environment — an explicit, documented, non-committed deviation from `ADR-0003`/`ADR-0004`, never this project's real local-dev setup) and logged into the running Admin UI against it. Verified via `curl`: `GET /sanctum/csrf-cookie` (204, sets cookies — real and functional, but confirmed **not** part of this backend's actual login flow, which is Sanctum bearer-token-only per `config/auth.php`'s own docblock and the absence of `statefulApi()` in `bootstrap/app.php`), `POST /api/v1/auth/login` (200, real token issued), `GET /api/v1/auth/me` (200, full role/permission payload) — all three match `packages/api-client`'s contract exactly.
  - **Bug found live, not by the mocked suite**: `permissionSet()` crashed (`Cannot read properties of undefined (reading 'flatMap')`) immediately after a real login, taking down the entire authenticated shell. Root cause: `AuthController::login()` (apps/backend) does not eager-load the `roles` relation the way `GET /api/v1/auth/me` does, so `UserResource`'s `whenLoaded('roles')` omits the key entirely from a fresh login response — invisible to Phase 2.1's own Playwright mocks because they included `roles` in the mocked login response, which the real backend never does.
  - **Fixed** in `apps/admin/src/auth/useAuth.ts`: `login()` now re-fetches `GET /auth/me` immediately after a successful login and uses that fully-loaded user for the session — both fixing the crash and ensuring the Sidebar's permission-aware rendering has the real permission set from the very first authenticated render, not only after a later page refresh. `permissionSet()` (`apps/admin/src/auth/permissions.ts`) also gained a defensive `user?.roles` check as belt-and-suspenders correctness, with a new regression test. `apps/admin/e2e/mocks.ts`'s `mockLoginSuccess` was corrected to return a login response **without** `roles` (matching the real backend), so this exact class of bug can never again pass the mocked suite silently.
  - **No AdminUserSeeder exists in this codebase — by deliberate, already-documented design** (`DatabaseSeeder`'s own docblock: seeding a default account with a known password would violate `SECURITY:SECURE_CONFIGURATION`). The accepted mechanism is `php artisan identity-access:create-admin`, a CLI command requiring an interactively-supplied or explicitly-flagged password. Used to create a real development administrator account for this verification pass.
  - Re-verified after the fix: fresh login (cleared `localStorage`, brand-new browser tab, zero console errors), Dashboard loads, Sidebar loads, User Menu opens (Profile/Sign out), Sign out returns cleanly to `/login`, and session restore after a hard page reload renders the shell directly with no login flash — all against the real running backend, not mocks. Full quality gate re-run: typecheck/lint clean, 23/23 `apps/admin` unit tests, 11/11 Playwright e2e (now against the corrected mocks).

  - **Critical, platform-wide security/correctness finding, found and fixed**: a live smoke-test request made with a plain HTTP client (no `Accept: application/json` header — unlike every automated test in this suite, which uses Pest's `getJson`/`postJson` helpers that always send one) to an unauthenticated, permission-protected endpoint returned a raw 500 Internal Server Error instead of the platform's intended clean 401 JSON envelope. Root cause: Laravel's default `Illuminate\Auth\Middleware\Authenticate::redirectTo()` calls `route('login')` to decide where to send an unauthenticated *guest* request, evaluated eagerly, *before* `AuthenticationException` is even constructed, whenever the caller's `Accept` header doesn't ask for JSON — and this platform, being a pure API backend with no web/login surface at all (`bootstrap/app.php`'s own exceptions block already documents "no HTML surface at all"), has no `login` route, so that call always threw `RouteNotFoundException` instead, bypassing the existing (correct, unconditional) `AuthenticationException` → 401 render mapping entirely. This affected **every permission-protected endpoint in every one of the 19 modules**, not just Search, for any real-world HTTP client that doesn't happen to send an `Accept: application/json` header — a genuine, previously-undetected gap between "verified by the automated test suite" and "verified live," and the reason this hardening pass's live smoke-testing step exists at all. Fixed with one line in `bootstrap/app.php`'s `withMiddleware()` block — `$middleware->redirectGuestsTo(fn (): ?string => null)` — so the framework never attempts to build a login redirect for any guest request, matching this API-only platform's own already-stated design intent. Two regression tests added (`tests/Feature/Domains/Platform/Foundation/Http/UnauthenticatedResponseTest.php`), deliberately using the raw `get()`/`post()` test helpers rather than `getJson()`/`postJson()`, specifically to keep exercising the no-`Accept`-header case the rest of the suite structurally cannot reach. Full Pest suite re-run afterward (1148 tests, 0 failures) to confirm zero regression from a change touching every module's authentication path.
