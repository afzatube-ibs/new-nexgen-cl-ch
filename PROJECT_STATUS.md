## What's Next

All 12 foundation documents (`00`–`11`) are Accepted. `ADR-0001`, `0002`, `0003`, `0004`, `0007`, and `0008` — the six Platform Foundation depends on — reached Accepted status on 2026-08-02 with Product Owner confirmation. `ADR-0005` (admin interface) and `ADR-0006` (storefront rendering) remain Draft until the modules that need them are reached.

**2026-08-03 resequencing:** the Product Owner directed that Catalog, Media, and Inventory be completed as one "Commerce Core" milestone ahead of `planning/IMPLEMENTATION_MASTER_PLAN.md`'s originally-listed Implementation Order. This was a sequencing change only — no constitutional document, ADR, or the master plan's own content required a correction.

**2026-08-05:** `planning/reviews/PHASE1_BACKEND_COMPLETION_REPORT.md` found Backend Phase 1 **not complete** — 14 of 19 modules built, 5 remaining (Shipping & Logistics, Fulfillment, Returns/Exchanges/Refunds, Notifications & Email, Search) plus the mandatory hardening pass, per that report's §6.

**2026-08-06:** Shipping & Logistics (basic) implemented per the Phase 1 completion report's §6 item 1, at `MODULE:SHIPPING`'s accepted scope only (method/zone/rate configuration and the rate-query Public Contract) — the Shipment execution/tracking/label responsibility the report's item 1 also touches on remains correctly scoped to the still-unbuilt Fulfillment module (item 2), per `docs/04_MODULE_ARCHITECTURE.md`'s existing `MODULE:SHIPPING`/`MODULE:FULFILLMENT` split.

**2026-08-07:** Fulfillment implemented per the Phase 1 completion report's §6 item 2 — pick/pack/dispatch workflow, courier reference tracking, fulfillment audit trail, reacting to `OrderPlaced`. Extended Shipping's `Couriers\ShippingProviderContract` additively (`bookShipment()`/`supportsBooking()`, exactly as that contract's own original docblock anticipated) rather than duplicating any courier-specific logic inside Fulfillment. Registered this platform's first real, production cross-domain event subscription (`ARCHITECTURE_REVIEW.md` A-4's anticipated first real subscriber) via a dedicated integration listener living outside every domain's own namespace, keeping both Orders and Fulfillment's own code free of any reference to the other.

**2026-08-08:** Returns/Exchanges/Refunds implemented per the Phase 1 completion report's §6 item 3. Extended Payments additively with refund columns/statuses and `RefundPaymentAction` (calling the `RefundableGateway` seam that module's own `bKash` gateway had left unexercised specifically for this). While building this module's own cross-domain listeners, a **self-review caught and fixed a platform-wide defect predating this delivery**: Laravel's automatic `app/Listeners` event auto-discovery (enabled by default since `Application::configure()`) was silently double-registering every cross-domain listener alongside this platform's own explicit `DomainEventBus::subscribe()` composition root in `AppServiceProvider`, including the pre-existing Fulfillment `CreateShipmentOnOrderPlaced` listener from 2026-08-07 — masked until now only because that handler happens to be idempotent. Fixed by disabling Laravel's discovery (`bootstrap/app.php`, `->withEvents(discover: false)`), leaving `app/Listeners/*` wired exclusively through the platform's own explicit contract.

**2026-08-08 (continued):** Notifications & Email implemented per the Phase 1 completion report's §6 item 4. `docs/04_MODULE_ARCHITECTURE.md` had never formally defined this module's boundary despite it being named in the master plan (only a passing mention under Localization & Currency's own entry); v1.4 adds it to Operations, reasoned through `ARCH:DOMAIN_MAP`'s own text rather than assumed — Platform is structurally ruled out (§10's "no Platform module may depend on any module outside Platform, directly or via events" — Notifications must react broadly to Commerce and Operations events), Growth is ruled out (`ARCH:DOMAIN_MAP` and `04_MODULE_ARCHITECTURE.md` §7 both state Growth is "designed for, not built in, Phase 1"), and Operations' own domain description ("reacts to events from Commerce... without owning Commerce's data") is an exact, already-exercised structural match. A **self-review caught and fixed a second, more severe platform-wide defect** introduced while building this module's eight cross-domain listeners: none of them originally caught their own exceptions, so a missing/misconfigured notification template (a routine, expected condition on a fresh installation) propagated straight back through the synchronous event bus into the *triggering* module's own transaction — surfacing as 24 unrelated test failures across Orders, Payments, Checkout, Customers, and Returns, since `OrderPlaced`/`PaymentCaptured`/`PaymentRefunded`/etc. are published from inside those modules' own core Actions. Fixed by wrapping every listener's notification-queuing call in a try/catch that reports and swallows the failure — a notification failure must never be able to break the workflow that triggered it, per this module's own "MUST NOT contain business logic from Orders, Payments, Shipping, Fulfillment, Returns, Customers... never the owner of business workflows" rule. A related reliability gap (a provider's own HTTP call throwing a raw connection-level exception, rather than returning a failed result, could leave a Notification stuck in `sending` forever) was found and fixed the same way.

**2026-08-08 (continued):** Search implemented per the Phase 1 completion report's §6 item 5 — the last business module before the hardening pass. `docs/04_MODULE_ARCHITECTURE.md` v1.5 formally adds `MODULE:SEARCH` to Commerce (the master plan names it, #29, with Catalog as its stated primary dependency — same-domain, needing no cross-domain event-routing bridge, a first for any module added this phase). Scope tension between the literal implementation instruction (Global/Product/Customer/Order/Store/Template/Audit search) and the accepted master plan (Catalog-index-only) was surfaced to the Product Owner via an explicit scope decision before implementation began, exactly as the Notifications SMS/WhatsApp scope tension was — resolved as Catalog-only Search plus small `q`-filter additions to Customers/Orders/Stores/Notification-templates' own existing list endpoints, each satisfying its own portion of "Customer/Order/Store/Template Search" within its owning module's already-accepted boundary. A genuine, non-obvious **testing-infrastructure finding**: InnoDB/MariaDB FULLTEXT indexes only consider committed data — a row inserted inside a test's own open transaction (this project's standard `RefreshDatabase` isolation, used by every prior module's test suite) is invisible to a real `MATCH ... AGAINST` query, which silently returned zero results for every FULLTEXT-dependent test until diagnosed. Fixed by adopting Laravel's `DatabaseTruncation` trait (real commits, truncated afterward) for the handful of tests that specifically exercise FULLTEXT relevance ranking — with an explicit `afterEach` cleanup added after discovering `DatabaseTruncation` only truncates *before* each test in its own file, never after, which would otherwise have leaked committed rows into every `RefreshDatabase`-isolated test class running later in the same process for the rest of the suite, not just this module's own tests.

**2026-08-08 (continued):** Phase 1 Hardening Pass completed — full production verification pipeline run and green (`composer test`: Deptrac 0 violations + Pest 1148/1148 passing against real MySQL/Redis; `composer analyse`: PHPStan/Larastan level 8, 0 errors across the whole codebase; Pint: clean across the whole codebase; `migrate:fresh --seed`: clean; `platform:health`/`/up`/`/api/health`: all healthy; live HTTP smoke test of the new Search endpoints, including a real Catalog product created through `CreateProductAction` and observed indexed automatically end-to-end through the real event bus). One PHPStan finding (an undefined-property access on a raw SQL `SELECT` alias in `ProductSearchResultResource`) and six Pint style findings were found and fixed.

A **critical, platform-wide finding surfaced only by live smoke testing**, not by the automated suite: an unauthenticated request made without an `Accept: application/json` header (every existing test uses Pest helpers that always send one) crashed with a raw 500 instead of the intended clean 401, on *every* permission-protected endpoint across *all 19 modules* — Laravel's default guest-redirect logic tried to build a `route('login')` URL this API-only platform has never had, throwing before the platform's own correct `AuthenticationException` → 401 mapping ever ran. Fixed with a one-line `redirectGuestsTo(fn (): ?string => null)` in `bootstrap/app.php`, with two new regression tests specifically exercising the no-`Accept`-header case, and the full 1148-test suite re-run clean afterward to confirm no regression from a change touching every module's authentication path. This is exactly the class of gap live verification exists to catch that a green test suite alone cannot.

Deployment review found `.github/workflows/backend-ci.yml` was missing a Pint (code style) gate — `composer test`/`composer analyse` were already wired, but a formatting regression could reach `main` uncaught — fixed by adding a `composer format:test` step. Two further, smaller gaps were identified and intentionally deferred to separate follow-up work rather than folded into this push, since neither blocks Phase 1 completion: the Notifications module's own `NOTIFICATIONS_*` environment variables were never documented in `.env.example` (unlike every other module), and `composer audit` could not be run in this session's sandbox (no `composer` binary available) to validate before wiring it into CI. **All 19 Phase 1 modules and the mandatory hardening pass are now complete.**
